# M3FX Project Plan

## Purpose

M3FX is a modular Material Design 3 component library for JavaFX. The project is still early enough to favor clean API and implementation shape over compatibility with earlier internal versions.

This file tracks product status and planning only. Repository rules, code style, nullability, documentation, Gradle invocation, and commit-message requirements belong in `AGENTS.md`.

## Current Baseline

- Java source and bytecode target: Java 17.
- Default JavaFX dependency for local builds and the demo app: JavaFX 21.
- Public implementation should stay compatible with JavaFX 14 APIs unless newer APIs are guarded by runtime checks or reflection.
- JavaFX is an application-owned dependency and is not published as an API dependency of the library.
- The JPMS module descriptor keeps transitive JavaFX readability because public APIs expose JavaFX types; this remains separate from Maven and Gradle artifact dependency publication.
- Material colors are generated through `org.glavo:MonetFX:0.4.0`.
- The demo app is a separate Gradle subproject.
- Theme and token APIs are token-first and profile-aware, with baseline M3 and M3 Expressive profiles represented separately.
- M3 Expressive currently has profile-specific color, typography, shape, component sizing, semantic motion scheme tokens, and motion behavior timings.
- M3 Expressive progress indicators use wavy linear and circular indicator geometry through profile-specific component tokens, and loading indicators use a dedicated animated shape sequence control with profile-specific metrics and default/contained variants.
- M3 Expressive action controls use profile-specific button padding, button group standard/connected variants, button group XS/S/M/L/XL size classes, connected button group spacing and inner-corner sizing, split button XS/S/M/L/XL size classes, split button spacing, action padding, menu sizing, and inner-corner sizing, FAB extended padding and menu spacing, segmented button padding, icon button XS/S/M/L/XL size roles, narrow/default/wide width roles, round/square shape roles, selected/pressed shape rules, outlined stroke widths, icon toggle spacing, tab indicator metrics, icon sizes, chip flat/elevated container style metrics, chip icon/avatar/outline tokens, and chip group spacing.
- M3 Expressive inputs, selection controls, and sliders use profile-specific input padding, selection touch target and state-layer metrics, checkbox/radio indicator sizing, switch track/state-layer/handle metrics, slider track thickness, and thumb sizing.
- M3 Expressive navigation and list components use profile-specific spacing, padding, and selected-container shape tokens.
- M3 Expressive menus, search surfaces, picker surfaces, and sheets use profile-specific padding, item spacing, result spacing, result container shape, trailing action gap, day/time cell sizing, popup sizing, and drag-handle metrics.
- Menus support standard and vibrant color styles with baseline and M3 Expressive profile color mappings for containers, selected items, text, and state layers.
- M3 Expressive forms and validation summaries use profile-specific row spacing, section spacing, label width, row height, summary padding, and invalid-item geometry.
- M3 Expressive surfaces and carousels use profile-specific surface padding, container shape, carousel track padding, item spacing, item opacity, and selected-item shadow metrics.
- M3 Expressive cards, dialogs, snackbars, app bars, and toolbars use profile-specific container shape, padding, height, and content/action slot metrics.
- Theme installation marks roots with profile and brightness style classes so applications and demo pages can branch CSS for baseline, expressive, light, and dark modes without replacing the theme API.
- Scene-level theme installation follows runtime scene-root replacement, temporarily overlays the current root, restores any previous local root theme when the root leaves the scene, and clears scene-owned declarations when uninstalled.

## Architecture

- `org.glavo.m3fx.theme` owns theme creation, scene installation helpers, stylesheet installation, and token stylesheet generation.
- `org.glavo.m3fx.tokens` owns color, typography, shape, elevation, motion, state-layer, density, profile, and component token groups.
- Public theme and token abstractions use sealed interfaces; implementations live in internal packages.
- `org.glavo.m3fx.animation` owns reusable Material motion durations and easing curves.
- `org.glavo.m3fx.internal` owns shared runtime infrastructure such as theme resolution, generated stylesheet caching, popup context propagation, focus guards, and logical layout helpers.
- `org.glavo.m3fx.controls` owns public controls, foundation primitives, and composition containers.
- `org.glavo.m3fx.skins` owns custom skins for layout, drawing, interaction, state layers, ripple, and animation behavior. Custom skins inherit JavaFX base skin classes such as `SkinBase`, `LabeledSkinBase`, or project skin bases. `PopupControl` skins use a project popup skin base because JavaFX `SkinBase` only accepts `Control` skinnables; tests reject concrete JavaFX skin inheritance and direct `Skin` implementations.
- Foundation primitives such as `M3Icon` and `M3Text` support components but are not standalone Material component pages.
- `M3Icon` is an icon glyph primitive for Material Symbols or fallback text. It is not focus-traversable by default; standard interactive component mappings belong to icon buttons, navigation items, app bars, menus, lists, and other controls that use icon slots.
- Public control APIs prefer constructors and explicit mutable properties over static convenience factories or narrow convenience setters. The controls package currently exposes no public `with`, `of`, or `create` factory methods, and count badges are created through constructors plus ordinary text mutation.
- Public component token records expose canonical record constructors only; source-style tests reject public token-record convenience constructor overloads so theme authors use explicit token values.
- Action, selection, menu, list, tab, navigation, container, feedback, and progress controls avoid inheriting from concrete JavaFX controls such as `Button`, `ToggleButton`, `CheckBox`, `RadioButton`, `MenuButton`, `ListView`, `Slider`, `ProgressBar`, `ProgressIndicator`, and `Tooltip`; tests enforce these boundaries. Text input controls intentionally retain JavaFX text input base classes to preserve editing, selection, clipboard, IME, and multiline behavior.
- Controls use per-control user-agent stylesheets where JavaFX supports them. Popup-only styling remains in dedicated control CSS files loaded through the base stylesheet.
- `M3ThemeManager` is a convenience installer, not a required runtime dependency for applications.
- The root style classes `m3-profile-baseline`, `m3-profile-expressive`, `m3-light`, and `m3-dark` describe the installed theme mode for application-level CSS.

## Implemented Areas

### Build And Distribution

- Multi-project Gradle build for the library and demo app.
- Java module descriptors for the library and demo app.
- Demo run, shadow jar, and jlink runtime-image tasks.
- Demo shadow jar excludes JavaFX artifacts.
- Demo shadow jar verification checks for an executable manifest and rejects bundled JavaFX entries.
- Local `releaseCheck` aggregates `check`, `shadowDemoJar`, and the default `jlinkDemoRuntime` so host-platform release validation has a single entry point without forcing all-platform JDK downloads.
- Publication metadata verification generates the Maven POM, rejects stale copied metadata, enforces the M3FX display name and optional static annotation metadata, and fails if JavaFX appears in published dependency metadata.
- Publication artifact verification checks the main jar and sources jar for required module, API, package, stylesheet, source, and bundled JavaFX implementation entries, while the javadoc jar is limited to artifact-shape checks without enforcing source comment or generated page coverage.
- Javadoc generation treats warnings as errors, so release documentation cannot ship with duplicate property comments, broken references, or other warning-level API documentation issues.
- Publication layout verification cleans and publishes the Maven publication to a build-local verification repository, then checks the real Maven repository layout, including timestamped SNAPSHOT artifact names, for exactly one main jar, sources jar, javadoc jar, and POM, disabled Gradle module metadata, and accidental JavaFX artifacts.
- Publication consumption verification resolves the build-local Maven publication through a Gradle consumer runtime configuration, requires M3FX and MonetFX in runtime resolution, and rejects transitive OpenJFX artifacts.
- Publication verification avoids execution-time Gradle `Project` access and root-project self-coordinate resolution, so `check --warning-mode all` stays free of Gradle 10 deprecation warnings.
- jlink support uses BellSoft LibericaJDK Full target jmods, platform-specific archive formats, and an automatically downloaded host `jlink` when cross-platform or cross-architecture builds need a matching Java feature executable.
- Platform and architecture-specific jlink tasks cover Windows, Linux, and macOS on x64 and AArch64, including the aggregate all-platform/all-architecture release validation task.
- jlink runtime tasks verify generated image structure before succeeding, including release metadata, linked modules, JavaFX runtime metadata, JavaFX legal metadata, M3FX demo module presence, and platform launcher files.
- Runtime packaging choices for library usage, demo shadow jars, and jlink images are documented in `docs/PACKAGING.md`.
- GitHub Actions runs `releaseCheck` under Xvfb, then uploads the verified demo shadow jar as an unarchived artifact, plus visual snapshot PNGs and Gradle test reports for failed-run or manual visual review.

## Validation Entry Points

- `compileJava` validates main source compilation.
- `check` validates generated publication metadata, publication jar contents, build-local Maven publication layout, and Gradle consumer resolution, then runs the default verification lifecycle.
- `javadoc` generates the public API documentation artifact.
- `test` validates unit, behavior, snapshot, and packaging tests.
- `releaseCheck` validates the library publication, executable demo shadow jar, and default demo jlink runtime image structure together.
- `shadowDemoJar` validates executable demo jar packaging without bundled JavaFX.
- `jlinkDemoRuntime` validates the default demo runtime image.
- Platform jlink tasks validate runtime images for Windows, Linux, and macOS.
- Architecture jlink tasks validate fixed x64 and AArch64 runtime images for each supported platform.

## Out Of Scope For Now

- Full M3 Expressive visual parity for every component.
- Web deployment for the JavaFX demo.
- SASS or another CSS preprocessor layer.
- High-complexity data components such as data tables.
